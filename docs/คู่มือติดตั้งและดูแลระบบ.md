# คู่มือติดตั้งและดูแลระบบ DATA BSTH

สำหรับผู้ดูแลเครื่องและผู้พัฒนาที่รับช่วงต่อ เรื่องโครงสร้างโค้ดดูเพิ่มที่ [README.md](../README.md)

---

## 1. ภาพรวม

```
เบราว์เซอร์ ──► Frontend (React + Vite, พอร์ต 5173) ──/api──► Backend (Fastify, พอร์ต 4000) ──อ่านอย่างเดียว──► HOSxP (MySQL)
                                                                   │
                                                                   ├── อ่าน/เขียน ──► data_dashboard (MariaDB) — เรื่องแจ้งปัญหา, ประวัติการใช้งาน
                                                                   └── backend/data/ — รูปแนบ, ผลที่พักไว้
```

- **HOSxP:** ใช้ตรวจ login (ตาราง `opduser`) และจะใช้ดึงรายงานเมื่อเปลี่ยนจากข้อมูลจำลอง เชื่อมต่อแบบ **อ่านอย่างเดียว** (SELECT เท่านั้น และตั้ง session เป็น READ ONLY)
- **data_dashboard:** ฐานของระบบเอง (`DASHBOARD_DB_*`) ถ้าไม่ได้ตั้งค่า ระบบจะเก็บเป็นไฟล์ใน `backend/data` แทน
- **ข้อมูลรายงานตอนนี้เป็นข้อมูลจำลอง** (`REPORT_DATA_SOURCE = 'mock'` ใน `backend/src/server.ts`)

## 2. สิ่งที่ต้องมี

- **Node.js 22 ขึ้นไป** (เครื่องพัฒนาใช้ 24) · เครื่องจริง: Linux + nginx (ดูข้อ 5.1)
- **สิทธิ์เชื่อมต่อฐาน HOSxP** (บัญชีที่ SELECT ได้) จากเครื่องที่ติดตั้ง
- **Telegram Bot** สำหรับแจ้งเตือนเรื่องแจ้งปัญหา (ไม่บังคับ)

## 4. ตั้งค่า `backend/.env`

ไฟล์นี้มีรหัสผ่าน **ห้ามส่งต่อ หรือนำขึ้น git** ถ้ารหัสผ่านมีอักขระพิเศษให้ใส่ในเครื่องหมายคำพูด `"..."`

| ค่า | ความหมาย | ค่าเริ่มต้น |
|---|---|---|
| `PORT` / `HOST` | พอร์ตและที่อยู่ของ backend | 4000 / 127.0.0.1 |
| `AUTH_SECRET` | ใช้เซ็น session — **ต้องเป็นค่าสุ่มยาว ๆ บนเครื่องจริง** | (ว่าง = ค่าทดสอบ) |
| `SESSION_IDLE_MINUTES` | ไม่ใช้งานกี่นาทีแล้วออกจากระบบ | 30 |
| `COOKIE_SECURE` | `true` เมื่อเปิดผ่าน https | false |
| `HOSXP_HOST` `HOSXP_PORT` `HOSXP_USER` `HOSXP_PASSWORD` `HOSXP_DATABASE` | การเชื่อมต่อ HOSxP | – |
| `HOSXP_ADMIN_GROUP` | ชื่อกลุ่มใน `opduser.groupname` ที่เป็นผู้ดูแลระบบ | ผู้ดูแลระบบ |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | แจ้งเตือนเรื่องแจ้งปัญหา (หลายปลายทางคั่นด้วย `,`) | ว่าง = ไม่ส่ง |
| `APP_PUBLIC_URL` | ลิงก์ https ของเว็บ สำหรับปุ่ม "เปิดดูในระบบ" ใน Telegram | ว่าง = ไม่มีปุ่ม |
| `TELEGRAM_ALERT_CHAT_ID` | ปลายทางแจ้งเตือนระบบล่ม / ดึงข้อมูลไม่ได้ (คั่นด้วย `,`) | ว่าง = ใช้ `TELEGRAM_CHAT_ID` |
| `ALERT_DOWN_MINUTES` | ล่มติดกันกี่นาทีจึงแจ้ง (แจ้งเฉพาะเครื่องจริง `NODE_ENV=production`) | 5 |
| `CACHE_PREWARM_MINUTES` | รอบเตรียมข้อมูลล่วงหน้า (นาที) | 30 |
| `CACHE_TTL_TODAY_MINUTES` / `CACHE_TTL_PAST_HOURS` | อายุผลที่พักไว้: ช่วงที่รวมวันนี้ / ช่วงในอดีต | 30 นาที / 24 ชม. |
| `HOSXP_MAX_CONCURRENT` | query ไป HOSxP พร้อมกันได้สูงสุด | 2 |
| `AUDIT_KEEP_DAYS` | ประวัติการใช้งานเก็บในไฟล์หลักกี่วัน | 180 |
| `MEM_WARN_MB` / `MEM_FREE_WARN_PCT` | เตือนเมื่อ backend ใช้ RAM เกิน / RAM เครื่องเหลือน้อยกว่า | 1024 MB / 5% |
| `DATA_WARN_MB` | เตือนเมื่อโฟลเดอร์ data ใหญ่เกิน | 500 MB |
| `LOG_IP_RATE_PER_MIN` | เตือนเมื่อ IP เดียวส่ง request เกิน (ครั้ง/นาที) | 300 |
| `DASHBOARD_DB_HOST` `DASHBOARD_DB_PORT` `DASHBOARD_DB_USER` `DASHBOARD_DB_PASSWORD` `DASHBOARD_DB_DATABASE` | ฐาน data_dashboard (อ่าน/เขียน) เก็บเรื่องแจ้งปัญหา + ประวัติการใช้งาน | ว่าง = เก็บเป็นไฟล์ |
| `SSE_MAX_CLIENTS` | จำนวนหน้าเว็บที่ต่อช่องสัญญาณสดพร้อมกันได้สูงสุด (1 เบราว์เซอร์ใช้ 1 เส้น ไม่ว่าเปิดกี่แท็บ) · เกินแล้วหน้าเว็บตรวจสถานะทุก 1 นาทีแทน | 500 |
| `SSE_MAX_PER_IP` | ช่องสัญญาณสดต่อเครื่อง (IP) สูงสุด — เกินแล้วเครื่องนั้นตรวจสถานะทุก 1 นาทีแทน | 20 |
| `LOGIN_MAX_IP_FAILS` | login ผิดรวมทุกชื่อผู้ใช้จากเครื่องเดียวภายใน 5 นาที เกินแล้วพักทั้งเครื่อง 5 นาที (นอกจากพักรายบัญชีเมื่อผิด 5 ครั้ง) | 30 |
| `DATA_DIR` | ย้ายโฟลเดอร์เก็บข้อมูลไปที่อื่น | backend/data |

**ตั้งค่า Telegram (ในโฟลเดอร์ backend)**
- `npm run telegram:chat-id`: หาเลข chat id หลังจากส่งข้อความหาบอทแล้ว
- `npm run telegram:test`: ส่งข้อความทดสอบ

## 5.1 ติดตั้งบนเครื่อง server (Linux)

```
ผู้ใช้ ──► nginx (พอร์ต 80/443) ──┬── หน้าเว็บที่ build แล้ว (frontend/dist)
                                  └── /api ──► backend (node, 127.0.0.1:4000) ← systemd ดูแล เปิดเอง/ดับแล้วเปิดใหม่
```

ไฟล์ที่เตรียมไว้ในโฟลเดอร์ `deploy/`:

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `deploy/nginx/bsth-dashboard.conf` | เสิร์ฟหน้าเว็บ + ส่ง `/api` ให้ backend · ไม่พักข้อมูลช่องสัญญาณสด · ส่ง IP เครื่องผู้ใช้จริง · แคชไฟล์หน้าเว็บ (ยกเว้น index.html) · ตัวอย่าง HTTPS |
| `deploy/systemd/bsth-dashboard.service` | ให้ backend เปิดเองตอนเปิดเครื่อง ดับแล้วเปิดใหม่ใน 5 วินาที · รันด้วยบัญชี `bsth` (ไม่ใช่ root) · เขียนได้เฉพาะโฟลเดอร์ data |
| `deploy/scripts/deploy.sh` | อัปเดตในคำสั่งเดียว: git pull → ติดตั้ง → ทดสอบ → build → รีสตาร์ท → ตรวจว่าขึ้น |
| `deploy/scripts/backup.sh` | สำรองฐาน data_dashboard + โฟลเดอร์ data ทุกคืน เก็บ 30 วัน |
| `deploy/scripts/watchdog.sh` | เฝ้า backend จากภายนอกทุกนาที — ไม่ตอบเกิน 5 นาทีแจ้งผู้ดูแลทาง Telegram · กลับมาแจ้งอีกครั้ง |
| `backend/.env.production.example` | ค่าตั้งสำหรับเครื่องจริง (★ = ต้องกรอก) |
| `npm run check:connections` | ตรวจความพร้อม: Node.js, เวลาไทย, AUTH_SECRET, สิทธิ์เขียนโฟลเดอร์ data, ต่อ HOSxP / data_dashboard ได้ไหม (อ่านอย่างเดียว) |

### สิ่งที่ต้องได้จากผู้ดูแล server ก่อน

- Linux รุ่นไหน (คำสั่งด้านล่างเป็น Ubuntu/Debian · Rocky/RHEL ใช้ `dnf` แทน `apt`)
- **server ต่อถึง HOSxP และฐาน data_dashboard ได้** — ตรวจเป็นอย่างแรก (ขั้นที่ 4) ถ้าไม่ได้ต้องขอเปิด firewall
- ผู้ใช้เข้าเว็บด้วยชื่ออะไร (IP / ชื่อโดเมนภายใน) และต้องเข้าจากนอกโรงพยาบาลไหม (ถ้าใช่ ต้องทำ HTTPS)
- บนเครื่องมี nginx หรือเว็บอื่นใช้พอร์ต 80 อยู่แล้วไหม
- บัญชี ssh ที่ใช้ sudo ได้

### ติดตั้งครั้งแรก

```bash
# 1) โปรแกรมที่ต้องใช้ — Node.js 24, nginx, git, mysqldump (ใช้สำรองฐาน)
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt install -y nodejs nginx git mariadb-client
sudo timedatectl set-timezone Asia/Bangkok          # ระบบคิดวันที่ตามเวลาไทย (backend บังคับเองอีกชั้น)

# 2) บัญชีที่รันระบบ (ไม่ใช่ root) + ดึงโค้ด
sudo useradd --system --create-home --shell /bin/bash bsth
sudo mkdir -p /opt/bsth-dashboard && sudo chown bsth:bsth /opt/bsth-dashboard
sudo -u bsth git clone https://github.com/rapepan/Data_Dashboard.git /opt/bsth-dashboard

# 3) ค่าตั้ง — กรอกช่องที่มี ★ (AUTH_SECRET สุ่มด้วย: openssl rand -hex 32)
cd /opt/bsth-dashboard
sudo -u bsth cp backend/.env.production.example backend/.env
sudo -u bsth chmod 600 backend/.env
sudo -u bsth nano backend/.env
sudo -u bsth mkdir -p backend/data
# QR Code LINE (หน้าติดต่อผู้พัฒนา) ไม่อยู่ใน git — คัดลอกไฟล์ line-qr.jpg ไปไว้ที่ backend/assets/ เอง

# 4) ตรวจความพร้อม — ต้องขึ้น "✔ พร้อมใช้งาน" ก่อนไปต่อ
sudo -u bsth npm ci --prefix backend
sudo -u bsth npm run check:connections --prefix backend

# 5) backend ให้ systemd ดูแล
sudo cp deploy/systemd/bsth-dashboard.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable bsth-dashboard

# 6) build + เปิดระบบ (สคริปต์เดียวกับที่ใช้อัปเดต)
sudo -u bsth SKIP_PULL=1 bash deploy/scripts/deploy.sh

# 7) nginx — แก้ server_name ในไฟล์ให้เป็นชื่อเว็บ/IP ก่อน
sudo cp deploy/nginx/bsth-dashboard.conf /etc/nginx/sites-available/bsth-dashboard
sudo ln -s /etc/nginx/sites-available/bsth-dashboard /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default        # ถ้าเครื่องนี้ไม่มีเว็บอื่น
sudo nginx -t && sudo systemctl reload nginx
sudo ufw allow 'Nginx Full' 2>/dev/null || true     # ถ้าเปิด firewall ของเครื่องไว้

# 8) สำรองข้อมูลทุกคืน 02:30
sudo mkdir -p /var/backups/bsth-dashboard && sudo chown bsth:bsth /var/backups/bsth-dashboard
sudo -u bsth bash deploy/scripts/backup.sh          # ลองรัน 1 ครั้ง
sudo -u bsth crontab -e                             # เพิ่มบรรทัด:
#   30 2 * * * bash /opt/bsth-dashboard/deploy/scripts/backup.sh >> /var/backups/bsth-dashboard/backup.log 2>&1

# 9) แจ้งผู้ดูแลทาง Telegram เมื่อเว็บล่ม — ทดสอบส่งก่อน แล้วเพิ่มใน crontab เดียวกัน:
sudo -u bsth bash deploy/scripts/watchdog.sh --test
#   * * * * * bash /opt/bsth-dashboard/deploy/scripts/watchdog.sh
```

**การแจ้งเตือนระบบล่ม (Telegram)** — ส่งไป `TELEGRAM_ALERT_CHAT_ID` (ว่าง = `TELEGRAM_CHAT_ID`) เฉพาะเครื่องจริง:

| เหตุการณ์ | ใครแจ้ง | เมื่อไร |
|---|---|---|
| ต่อ HOSxP / ฐาน data_dashboard ไม่ได้ | backend (ตรวจทุก 1 นาที) | ติดกันเกิน 5 นาที · กลับมาแจ้งอีกครั้งพร้อมบอกว่าล่มนานเท่าไร |
| backend ดับโดยไม่ได้ตั้งใจแล้วเปิดกลับมา | backend | ตอนเปิดกลับมา (systemd เปิดใหม่ให้ใน 5 วินาที) |
| เว็บไม่ตอบ (backend ค้าง / เปิดไม่ขึ้น) | `watchdog.sh` (cron ทุกนาที) | ติดกันเกิน 5 นาที · กลับมาแจ้งอีกครั้ง |
| ดึงข้อมูลรายงานจาก HOSxP ไม่สำเร็จหลายรอบ | backend (มีอยู่เดิม) | ล้มติดกันหลายรอบ · กลับมาแจ้งอีกครั้ง |

ล่มสั้นกว่า 5 นาทีไม่แจ้ง · ถ้าทั้งเครื่อง server ดับหรือเครือข่ายขาด จะไม่มีใครแจ้งได้ (ต้องเฝ้าจากเครื่องอื่น)

> **บัญชี `bsth` ต้องรีสตาร์ท service ได้** (deploy.sh ใช้ `sudo systemctl restart`) — ให้สิทธิ์เฉพาะคำสั่งนี้:
> `echo 'bsth ALL=(root) NOPASSWD: /usr/bin/systemctl restart bsth-dashboard' | sudo tee /etc/sudoers.d/bsth-dashboard`

ตรวจหลังติดตั้ง: เปิดเว็บด้วยชื่อ/IP ของ server → login ได้ → หน้า "ประกาศ / ปิดปรับปรุง" เปิด/ปิดโหมดแล้วหน้าเว็บอีกเครื่องเปลี่ยนทันที (ช่องสัญญาณสดผ่าน nginx ได้) → หน้า "ผู้ใช้งานระบบ" เห็น IP เครื่องผู้ใช้จริง (ไม่ใช่ 127.0.0.1)

### อัปเดตระบบ (ครั้งต่อไป)

```bash
cd /opt/bsth-dashboard
sudo -u bsth bash deploy/scripts/deploy.sh
```

ทำตามขั้นตอนแจ้งผู้ใช้ในข้อ 8.1 (ประกาศล่วงหน้า / เปิดโหมดปิดปรับปรุง) ถ้าการอัปเดตกระทบการใช้งาน · ถ้าหน้าเว็บใหม่มีปัญหา ย้อนกลับได้ทันที: `mv frontend/dist frontend/dist-bad && mv frontend/dist-prev frontend/dist`

### ดูแลประจำ

| ต้องการ | คำสั่ง |
|---|---|
| ดูสถานะ backend | `systemctl status bsth-dashboard` |
| ดูข้อความ backend สด ๆ (เหมือนเทอร์มินัลตอน dev) | `journalctl -u bsth-dashboard -f` |
| ดูข้อความวันนี้ / 100 บรรทัดล่าสุด | `journalctl -u bsth-dashboard --since today` · `-n 100` |
| รีสตาร์ท backend | `sudo systemctl restart bsth-dashboard` |
| ตรวจการเชื่อมต่อฐานข้อมูลอีกครั้ง | `sudo -u bsth npm run check:connections --prefix /opt/bsth-dashboard/backend` |
| ดูไฟล์สำรอง | `ls -lh /var/backups/bsth-dashboard` · log: `backup.log` ในโฟลเดอร์เดียวกัน |

**ข้อควรรู้**
- backend ต้องรัน **ตัวเดียว** — สถานะออนไลน์ ช่องสัญญาณสด และตัวตั้งเวลาปิดปรับปรุงอยู่ในหน่วยความจำ (ห้ามรันหลาย instance)
- หน้าเว็บไม่ต้องออกอินเทอร์เน็ต — Bootstrap / ไอคอน / ฟอนต์ รวมอยู่ในไฟล์ที่ build แล้ว (Telegram ยังต้องให้ server ออกไป api.telegram.org ได้)
- ขึ้นเวอร์ชันใหม่ (`version` ใน package.json) แล้วรัน deploy.sh — หน้าเว็บที่เปิดค้างไว้จะขึ้นกล่องให้ผู้ใช้กดรีเฟรชเอง

## 8. อ่านข้อความในเทอร์มินัล backend

| ข้อความ | ความหมาย |
|---|---|
| `GET 200 /api/... · ผู้ใช้ · IP · 12ms` | request ทั่วไป (สีเหลือง = 4xx, สีแดง = 5xx, `⚠ ช้า` = เกิน 1 วินาที) |
| `[auth]` | login / logout / login ผิด / session หมดอายุ / ⛔ เข้าส่วนที่ไม่มีสิทธิ์ |
| `[admin] 👁` | ผู้ดูแลเปิดหน้าผู้ดูแลระบบ |
| `[export]` | ส่งออก Excel / PDF |
| `[client] ✖` | error ที่เกิดในเบราว์เซอร์ของผู้ใช้ |
| `[hosxp]` | เวลา query HOSxP / การเชื่อมต่อหลุดหรือกลับมา |
| `[cache]` `[prewarm]` | โหลดรายงานใหม่ / รอบเตรียมข้อมูลล่วงหน้า |
| `[feedback]` `[notify]` | เรื่องแจ้งปัญหาใหม่ / ผลการส่ง Telegram |
| `[audit]` | ย้ายประวัติเก่าเข้าคลัง |
| `[เฝ้าระวัง] ⚠` | RAM สูง · พื้นที่ข้อมูลใหญ่เกิน · IP ส่ง request ถี่ผิดปกติ |
| กล่อง **สรุป 1 ชั่วโมง** | request, ผู้ใช้, ความเร็ว, error, หน้าที่เปิดมากสุด, RAM |
| กล่อง **สรุปทั้งวัน** | พิมพ์ตอนเที่ยงคืน: ผู้ใช้, login, หน้าที่เปิดมากสุด, ส่งออกไฟล์, เรื่องแจ้งใหม่, พื้นที่ข้อมูล |
| กล่องสีแดง **✖ error ที่ไม่ได้ดักไว้** | เกิด error ที่โค้ดไม่ได้ดักไว้ ถ้าเป็น uncaughtException เซิร์ฟเวอร์จะปิดตัว ต้องเปิดใหม่ |

ระบบไม่พิมพ์รหัสผ่าน, token, ข้อมูลเชื่อมต่อฐาน หรือคำค้นใน URL ลงเทอร์มินัล

## 8.1 ขั้นตอนอัปเดตระบบ (แจ้งผู้ใช้)

1. **ประกาศล่วงหน้า** — หน้า "ประกาศ / ปิดปรับปรุง" → สร้างประกาศระดับ "เตือน" เช่น 1–2 วันก่อน · ติ๊ก "ระบุเวลาปิดปรับปรุงจริง" (และ "อัตโนมัติ" ถ้าต้องการให้ระบบเปิด/ปิดโหมดเอง)
2. **ตอนเริ่มอัปเดต** — ถ้าแก้แค่บางหน้า ใช้ "ปิดปรับปรุงเฉพาะหน้า" (หน้าอื่นใช้ได้ต่อ) · ถ้ากระทบทั้งระบบ กด "เปิดโหมดปิดปรับปรุง" (ใส่ข้อความเวลาที่คาดว่าจะเสร็จ) · ผู้ใช้ทั่วไปที่เปิดเว็บค้างไว้เห็นหน้าปิดปรับปรุงทันที (ช่องสัญญาณสด ไม่ต้องรีเฟรช) ผู้ดูแลยังใช้งานได้
3. **อัปเดตโค้ด** — แก้เลข `version` ใน `package.json` ที่โฟลเดอร์หลัก (เช่น 0.1.0 → 0.2.0) และเพิ่มรายการบนสุดของ `frontend/src/config/changelog.ts` (ถ้าต้องการให้ขึ้นหน้าต่าง "มีอะไรใหม่") · **แบบ dev ต้องให้หน้าเว็บอ่านเลขใหม่ด้วย**: รีสตาร์ท frontend หรือแตะไฟล์ `frontend/vite.config.ts` (บันทึกซ้ำ) — Vite ไม่ได้เฝ้าดู package.json ถ้าไม่ทำ ผู้ใช้กดรีเฟรชแล้วยังเป็นเลขเดิม กล่องแจ้งอัปเดตจะขึ้นซ้ำ · แบบ build ต้อง build หน้าเว็บใหม่
4. **รีสตาร์ท / build** — ระหว่าง backend ปิด ผู้ใช้เห็น "กำลังอัปเดตระบบ" แล้วกลับมาเองเมื่อ backend ขึ้น (หน้าเว็บตรวจทุก 10 วินาที)
5. **ตรวจระบบในฐานะผู้ดูแล** แล้วกด "ปิดโหมด" — หน้าเว็บที่เปิดค้างไว้จะขึ้นกล่อง "ระบบอัปเดตเป็น V 0.2.0 แล้ว [รีเฟรช]"

> ตอนรันแบบ dev: เลขเวอร์ชันของหน้าเว็บอ่านตอนเริ่ม Vite — แก้เลขเวอร์ชันแล้วต้องเริ่ม `npm run dev` ใหม่ ไม่งั้นกล่องแจ้งเวอร์ชันใหม่จะยังขึ้นหลังรีเฟรช

## 10. เปลี่ยนจากข้อมูลจำลองเป็นข้อมูลจริง

แก้ที่ `backend/src/cache/report-registry.ts` ทีละรายงาน
1. เปลี่ยน `load` ให้เรียก query HOSxP (ผ่าน `timedQuery` อ่านอย่างเดียว) และคืนข้อมูลรูปแบบเดิม
2. เปลี่ยน `source` เป็น `'hosxp'`
3. เพิ่มเลข `version` ของรายงานนั้น เพื่อล้างผลที่พักไว้ชุดเก่า

หน้าเว็บและระบบพักผลไม่ต้องแก้ ก่อนเปลี่ยนต้องยืนยันกับโรงพยาบาลก่อน:
- ความหมายของช่องเวลาในตาราง `service_time`
- เป้าหมายเวลาแต่ละขั้น (SLA)
- นิยาม IMC
- การจัดหมวดหัตถการแพทย์แผนไทย
- การนับนัดยกเลิก / ไม่มาตามนัด

**แผงที่ซ่อนไว้** (ไม่มีข้อมูลในฐาน) เปิดกลับได้ที่ `frontend/src/config/features.ts` ส่วนหน้า Stroke Unit ซ่อนไว้ที่ `routes/index.ts` และ `navigation.ts`
